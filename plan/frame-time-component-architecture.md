# Samsara 组件级帧时序与可选插值架构计划

> 状态：架构储备，待实际需求触发。不是当前相机修复的一部分，也不代表已经批准全面实施。
>
> 前置基础：`../child_of_a_thousand_stars/plan/10_fixed_simulation_and_frame_updates.md` 中的固定步长调度器、场景级 `updateFrame(realDt)` 和 `simulationInterpolation`。

## 1. 保存本计划的原因

场景级显示帧钩子可以解决相机等少量场景逻辑，但实时游戏随后可能遇到两类更细的问题：

- 某些纯视觉组件需要每个显示帧更新，而不是只在固定 60Hz tick 中更新。
- 飞船、子弹等玩法实体仍按固定 tick 移动，在高刷新率下需要显示插值才能避免阶梯运动。

这些问题适合由 Samsara 提供少量通用协议，但不应因此重写所有组件或建立一套完整动作游戏引擎。本计划用于保存边界、推荐方向和实施闸门；只有实际项目出现对应需求时才按阶段采用。

## 2. 核心原则

- 固定逻辑更新与显示帧更新是两个显式入口，同一个组件不能在同一阶段被两条路径隐式推进两次。
- 现有 `Component.update(dt)` 继续保持固定步长语义，既有卡牌、对话和界面组件默认不变。
- 显示帧能力是场景级可选能力，不让所有场景无条件承担额外组件遍历成本。
- 插值只改变渲染，不写回逻辑位置、碰撞形状、速度、伤害或实体生命周期。
- 优先提供协议和小型工具，不引入物理、AI、ECS、通用战斗系统或新的实体架构。
- 每个阶段可以独立停止；后续阶段不是前一阶段的必然后果。

## 3. 阶段 A：可选的组件显示帧更新

### 3.1 目标

允许实时场景中的少数纯视觉组件接收真实 `dt`，同时保持其他组件只执行固定逻辑 tick。

建议增加轻量接口或 mixin，名称可在实施时遵循现有代码风格，例如：

```dart
mixin FrameUpdatable on Component {
  void updateFrame(double dt);
}
```

它只定义显示帧入口，不改变组件的固定 `update()`。

### 3.2 场景调度顺序

推荐顺序：

```text
Scene.updateTree(realDt)
→ 执行 0～N 个固定逻辑 tick
→ 调用场景级 updateFrame(realDt)
→ 对启用的组件树调用 updateFrame(realDt)
→ 渲染
```

场景级相机先更新，视差等组件随后读取最新相机，避免同一显示帧使用两代相机位置。

只有显式开启组件显示帧更新的场景才执行组件树路径。默认场景没有额外遍历，也不需要修改现有子类。

### 3.3 遍历与安全约束

- 首版可使用明确的组件树遍历验证语义，但必须限制在启用的场景，不能用全局事件总线分发。
- 每个挂载且实现接口的组件每帧最多调用一次，包括没有固定 tick 的帧。
- 父组件和子组件都实现接口时，各自只调用一次，不因递归和父级转发重复执行。
- 新增、移除组件沿用 Flame 的安全组件树操作方式，不在遍历中直接破坏当前集合。
- 场景缓存、恢复和失焦后不得补执行离开期间积压的显示帧回调。
- 如果实际组件量证明逐帧遍历成本明显，再评估挂载时注册、卸载时注销的显式集合；不预先实现复杂注册系统。

### 3.4 首批适用对象

只在真实消费者需要时接入：

- 视差层。
- 纯视觉粒子、尾迹和扫描线。
- 不影响玩法结果的装饰动画。
- 需要与显示帧相机同步的调试绘制。

首版不迁移 `GameComponent.moveTo`、所有 Flame Effect、卡牌动画或既有界面组件。它们是否迁移必须逐项判断，不能按基类批量切换。

## 4. 阶段 B：可选的位置与角度插值

### 4.1 目标

为固定 tick 移动的实体提供独立显示状态，使高刷新率渲染不必直接呈现逻辑位置的阶梯变化。

建议提供小型值对象或 mixin，保存：

```text
previousSimulationPosition
simulationPosition
previousSimulationAngle
simulationAngle
simulationInterpolation
renderPosition / renderAngle
```

接口应允许实体在固定 tick 开始前保存上一状态，在显示帧计算插值状态。

### 4.2 逻辑与渲染隔离

这是本阶段最重要的约束：

- `position`、碰撞查询和战斗计算继续使用逻辑状态。
- 插值结果只用于相机目标或渲染变换。
- 不得在 `updateFrame` 中把插值位置写回 `position`，然后在下一固定 tick 把它当成逻辑起点。
- 实施时优先研究 Flame 的渲染变换入口，以额外渲染偏移或独立视觉变换实现，避免在 `renderTree` 前后临时篡改逻辑字段。
- 如果需要包装视觉子组件，应先做一个最小原型验证父组件变换、相机可见性判断和手势坐标，不直接批量修改 `GameComponent`。

### 4.3 插值语义

采用常见的上一逻辑状态到当前逻辑状态插值：

```text
render = previous + (current - previous) × simulationInterpolation
```

这会带来最多一个固定 tick 的显示延迟，必须在文档中明确。其收益是显示连续且不用预测未来逻辑状态；首版不做网络式外推或预测。

特殊情况：

- 新生成实体初始化上一状态等于当前状态，不能从原点或上一实体状态飞入。
- 传送、重生、场景恢复和相机瞬间定位时，将上一状态对齐当前状态，避免跨地图长距离扫过。
- 实体销毁后直接退出渲染，不为已删除对象保留插值残影。
- 角度使用最短弧插值，处理 `-π/π` 跨越。
- 父子组件不能重复叠加同一实体的插值偏移；首版只支持明确的根实体或明确的视觉子层。
- 相机跟随插值后的视觉位置，不能继续追踪另一套未插值目标。

### 4.4 不提前支持的内容

- 移动目标的连续碰撞或预测碰撞。
- 逻辑状态回滚、网络同步和确定性回放。
- 任意组件字段的通用快照。
- 全场景自动插值。
- 通过显示插值修正玩法命中位置。

## 5. 阶段 C：纯视觉能力的按需迁移

只有阶段 A 或 B 在真实场景证明有必要后，才逐项评估：

- `ParticleComponent` 与项目粒子是否支持显示帧更新。
- 视差组件是否提供固定、显示帧两种更新方式。
- 纯视觉 Effect 是否允许选择显示帧时钟。
- 动画是否只插值显示，或改为真实 `dt` 推进。

迁移时必须明确每个组件的唯一时钟。尤其是既包含玩法计时又包含视觉表现的组件，应先拆分职责，不能简单把整个组件移到 `updateFrame`。

既有卡牌、对话、富文本和 UI 动画保持现状，除非出现独立且可复现的问题。

## 6. 示例与文档

实际实施任一公共能力时，按 Samsara 现有约定同步：

- `docs/zh/core.md` 与 `docs/en/core.md`：固定 tick、显示帧、组件回调顺序和长帧策略。
- 如组件接口放入公共 barrel，补充对应组件文档及导出。
- 在 example 中增加一个最小时序演示，固定更新与显示帧更新使用可区分的计数或运动对象；不制作复杂游戏场景。
- 文档明确默认关闭、性能成本、一个 tick 的插值延迟，以及插值不影响碰撞的边界。
- 如实施前决定不采用某阶段，保留本计划并记录决策，不把构想描述成现有能力。

## 7. 验证计划

### 阶段 A

使用合成 `dt` 和最小测试组件验证：

- 30／60／120／144Hz 输入下，固定更新次数符合调度器规则，显示帧组件每个输入帧恰好更新一次。
- 没有固定 tick 的帧仍执行显示帧回调。
- 嵌套组件不重复更新，动态添加和移除安全。
- 未启用能力的场景没有组件显示帧回调，也没有新增遍历。
- 场景退出和恢复不补跑显示帧时间。

### 阶段 B

使用纯逻辑测试验证：

- 起点、终点、零移动、部分插值和余量边界。
- 角度跨 `-π/π` 时走最短方向。
- 新生、传送和重置不会产生长距离插值。
- 任意插值结果都不会修改逻辑位置和碰撞结果。
- 相机目标与实体渲染使用同一份插值状态。

### 性能与集成

- 在实际实时场景的组件数量下比较启用前后的更新耗时和临时对象分配。
- 运行 Samsara 既有测试、`flutter test` 与 `flutter analyze`，并检查 example。
- 画面流畅度、相机手感及输入准确性由使用方实际运行验收，不以测试或静态分析代替。

## 8. 实施闸门

为避免架构先于需求膨胀，按以下顺序决策：

1. 当前项目完成场景级相机与视差分离后，先实际验收。
2. 如果剩余问题只是少数纯视觉组件需要真实 `dt`，只实施阶段 A。
3. 如果主要问题是固定 tick 实体在高刷新率下的阶梯运动，优先原型验证阶段 B，不必先迁移全部视觉组件。
4. 只有公共能力出现第二个真实消费者，或当前项目明确需要复用时，才推广到 Samsara 既有组件。
5. 任一阶段如果引入的逻辑／渲染状态混淆大于收益，停止推广并保留场景级方案。

本计划的成功标准不是让所有组件支持双时序，而是让确有需要的实时组件能够以清晰、可选且不污染玩法状态的方式支持它。
